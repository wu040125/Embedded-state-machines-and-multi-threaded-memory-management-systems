# 02 固定对象池与对象生命周期

代码入口：

- `include/edge_sentinel/memory/fixed_object_pool.hpp`
- `tests/memory_pool_test.cpp`

## 为什么需要池

普通堆分配的耗时和碎片情况取决于分配器全局状态。嵌入式关键路径更关心：最大占用是否可知、分配失败是否可预测、退出时是否存在未归还对象。

对象池在构造时准备 `Capacity` 个槽位。每个槽位包含：

```text
alignas(T) raw storage[sizeof(T)]
next free index
occupied flag
```

空闲槽通过索引链连接。分配从链头取槽，回收时重新插入链头。

## 对齐

为 `T` 预留 `sizeof(T)` 字节还不够，起始地址还必须满足 `alignof(T)`。项目使用：

```cpp
alignas(T) std::array<std::byte, sizeof(T)> storage;
```

测试使用 64 字节对齐类型，并检查地址对 64 取模为 0。

## 存储与对象不是同一个概念

原始字节存在，不代表 `T` 对象已经存在。`std::construct_at` 在槽位中开始对象生命周期，`std::destroy_at` 结束生命周期并执行析构函数。

这就是为什么池不能只返回强制转换后的指针却从不调用构造和析构。

## 异常安全

对象构造在持锁状态下执行。如果构造函数抛出异常，空闲链头和占用统计尚未修改，槽位仍然可用。

当前约束是：池中对象的构造和析构不应重新调用同一个池，否则会造成锁重入。事件对象构造简单，不违反该约束。

## 为什么第一版使用互斥锁

无锁空闲链需要处理 ABA、内存回收次序和内存序。为了简历上的“无锁”标签引入隐蔽错误没有意义。

当前互斥实现具备：

- 行为清晰。
- ThreadSanitizer 可验证。
- 容量和延迟仍可测量。
- 后续可把无锁版本作为独立实验对照。

## 泄漏与非法释放

池统计包含：

- `in_use`
- `high_watermark`
- 成功分配和释放次数
- 分配失败次数
- 非法释放次数

`destroy()` 会区分外部指针和重复释放。正常代码应始终使用 `Handle`，手动 `release()` 只用于底层接口和测试。

这里的“泄漏检测”指池退出前仍有多少槽位处于占用状态，不等同于分析整个进程的所有堆内存。全进程检查由 ASan/LeakSanitizer 或 Valgrind 完成。

## 复杂度

- 分配：空闲链头操作，O(1)。
- 正常释放前的槽定位：当前线性扫描，O(Capacity)。
- 统计快照：O(1)。

释放扫描是一个刻意保留的简单设计。容量只有 256，且它允许可靠识别外部指针。若性能分析证明这里是瓶颈，再改成经过范围和步长验证的索引计算。
