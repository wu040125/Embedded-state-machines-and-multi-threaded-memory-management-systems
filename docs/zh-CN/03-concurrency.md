## 状态所有权比“到处加锁”更重要

只有控制线程调用 `MotorStateMachine::handle()`。其他线程只能发布事件。

这等价于把状态机放在只有一个窗口的房间里：所有修改请求排队进入，房间里永远只有一个人改状态。相比多个线程直接拿状态机互斥锁，这种设计更容易推理和回放。

快照读取仍使用短临界区互斥锁，防止监控线程看到撕裂的数据。

## 固定环形队列

队列使用 `std::array<std::optional<T>, Capacity>`，由 `head`、`tail` 和 `size` 管理。

```text
push: 在tail构造 -> tail前进 -> size增加
pop : 从head移动 -> 销毁槽位 -> head前进 -> size减少
```

容量满时有三种选择：

- `try_push` 立即返回 `full`。
- `wait_push` 等待指定时间。
- 队列关闭后返回 `closed`。

项目运行时使用有限等待。这样既不无限阻塞采集线程，也不会默默扩大内存。

## 条件变量为什么必须带谓词

条件变量可能伪唤醒，因此不能把“被唤醒”理解成“条件一定满足”。正确方式是：

```cpp
not_empty.wait(lock, [this] { return closed || size > 0; });
```

谓词还解决了通知发生在等待之前的情况，因为线程会先检查真实状态。

## 关闭语义

`close()`：

- 禁止新的 push。
- 唤醒所有等待生产者和消费者。
- 不丢弃队列中已有对象。
- 消费者排空后得到空值并退出。

这比简单设置一个 `running=false` 更完整。否则消费者可能永远睡在条件变量上。

## 锁顺序

当前关键顺序为：

- 发布：短暂锁池，释放后再锁队列。
- 消费：从队列移出句柄，释放队列锁后再锁状态机。
- 快照：锁状态机，再分别获取池和队列快照。

代码避免同时长期持有两个资源锁，从结构上降低死锁风险。

## 原子变量和内存序

运行状态使用 acquire/release，让观察到 `running=true` 的线程也能看到启动前写入的配置。纯计数指标使用 `memory_order_relaxed`，因为它们不承担发布其他数据的同步职责。

不要把所有原子操作都机械改成 relaxed。先问：这个原子是否用于发布另一块数据？

## 如何验证并发

- 队列测试运行四个生产者和一个消费者。
- 内存池测试运行四个并发分配者。
- `runtime_test` 运行完整采集、控制和监控线程。
- CI 的 ThreadSanitizer 独立运行。

测试通过不等于证明所有调度都正确，但它提供可重复证据，并让后续修改更安全。
